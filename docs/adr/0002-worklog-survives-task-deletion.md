# ADR-0002: 作業ログはタスク削除後も残し、記録時点のスナップショットを持つ

## ステータス

承認済み — 2026-08-30

## コンテキスト

作業ログ（WorkLog）は日報・週報の材料として AI に読ませて要約させることが主目的。
タスクやプロジェクトを整理（削除）した際に、過去の作業記録まで一緒に消えてしまうと、
先週・先月の日報が再生成できなくなり、機能の価値が失われる。

一方で、既存テーブル（`columns` / `tasks`）は全て `ON DELETE CASCADE` で統一されており、
`work_logs` だけ例外にすることは一貫性を崩すトレードオフを伴う。

また、削除済みタスクの表示名をどう扱うかも合わせて決める必要がある。

## 決定

- `work_logs.task_id` / `work_logs.project_id` に**外部キー制約を張らない**。
  タスク・プロジェクトが削除されても `work_logs` の行は残る。
- タスク名・プロジェクト名は**ログ作成時**に `task_title` / `project_name` としてスナップショットする。
  削除時に埋める方式は採らない。

## 理由

- タスクが消える経路は「タスク削除」「カラム削除の CASCADE」「プロジェクト削除の CASCADE」
  「CLI のプロジェクト削除」の4つあり、削除時にスナップショットを埋める方式だと全経路に
  フック実装が必要になる。実装漏れがあれば記録が欠損する。
- 記録時に書けば INSERT 1回で完結し、削除経路側のフックはゼロで済む。
- 日報の文脈では「作業した当時のタスク名」の方がむしろ正確（後からタスク名を変更・整理しても、
  当時の呼び方で日報が読める）。

表示・出力時は `tasks` / `projects` を `LEFT JOIN` し、
`COALESCE(現在名, スナップショット名)` で解決する。JOIN 結果が `NULL` であることが
「削除済みタスク・プロジェクトのログ」の判定にもなる。

## 却下案

- **`ON DELETE CASCADE`**（既存テーブルと一貫する）— タスクやプロジェクトを整理した瞬間に
  過去の作業記録が消え、日報の再生成ができなくなるため却下。
- **削除時にスナップショットを埋める**（記録時ではなく削除時に確定する）— 削除経路が複数あり
  実装・保守コストが高く、漏れのリスクがあるため却下。

## 既知のトレードオフ

タスク・プロジェクトを削除しても `work_logs` の行は残り続けるため、孤児レコードが溜まる。
掃除手段（`log prune --before <date>` 等）は今回実装しない。運用上必要になった時点で追加する。
